## 保留与转换

- 保留账号、租户、成员、组织、岗位、角色、资源等原 ID，以及姓名、联系方式、密码摘要、租户状态/到期时间和有效关系。
- 历史密码以明确的 `legacy-beehive$` 算法标记导入。旧密码验证兼容原系统，成功登录后升级 bcrypt。密码改变、账号停用、会话撤销与升级并发时，旧登录不能覆盖新状态。
- 原 `is_signal_login` 保留为 `users.single_login`，仅原本启用单会话的账号再次成功登录时撤销旧会话。原本允许多会话的账号保持不变。撤销使用账号 `auth_version`，与旧密码升级在同一事务提交；失败登录不撤销已有会话。
- 保留重复邮箱原值，移除数据库唯一邮箱约束；手机号仍唯一，邮箱登录多匹配时拒绝。
- 45 个单位原 `unit_id=0` 归一化为自己的组织 ID。
- 岗位 32 原组织 3、岗位 41 原组织 51 已不存在；它们的全部关联成员分别一致归属组织 46、52，依据这些关系修复。若关联成员不一致，导入器拒绝猜测并回滚。
- 旧首页组件映射到复用后的公共工作台，其他受支持页面保留原 resource code 和路径。不把旧菜单权限扩大成新模块全部写权限。
- 同 method/path 多旧绑定，仅在每个现存角色的有效授权和数据范围完全等价时采用确定的单一绑定，否则拒绝导入。
- 新旧数据集使用不同 Redis 会话命名空间，避免相同数字 user_id 使旧测试会话误认成真实用户。
- 头像和 LOGO 的旧相对 key 保留；网关使用 `KERTHUS_LEGACY_STATIC_URL` 跳转到原静态站点。新图片仍写本地 MinIO。本次未搬迁原对象存储的二进制文件，也不保证原静态站点持续可用。


在已确认源库和目标库身份映射一致后执行：

```sql
START TRANSACTION;
SELECT id FROM kerthus_saas.platform_lock WHERE id = 1 FOR UPDATE;
UPDATE kerthus_saas.users AS target
JOIN beehive_saas.d_user AS source
  ON target.id = source.id AND BINARY target.phone = BINARY source.phone
SET target.single_login = (source.is_signal_login <> 0)
WHERE target.single_login <> (source.is_signal_login <> 0);
COMMIT;
```

此补齐只写 `single_login`；不重导入账号、不覆盖已升级的 bcrypt、状态或其他资料。原始 62 个账号中 61 个启用单会话、1 个关闭。补齐后重启 Go 服务以启用登录策略。回归以独立 MySQL 库的合成账号验证手机号/邮箱登录、旧密码升级、单/多会话、错误密码不撤销会话及并发登录；不能将这些测试当作用户真实密码验收。
